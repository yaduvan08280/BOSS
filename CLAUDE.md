## 0. What we are building

**MONO** is a self-hosted, multi-module "business operating system": one web app where a company
sets up its people and structure once, then runs all daily work through it — delegated tasks,
recurring checklists, problem slips, help tickets, an executive-assistant (EA) board, step-by-step
business processes (FMS), HR attendance/leave with automatic "Buddy" cover, inventory rules (IMS),
and a sales CRM with a year plan. Every piece of work has an **owner, a planned time and a verifier**,
and a **scheduler** sends reminders and escalations over **Telegram, WhatsApp, email and in-app**.
An **AI layer** drafts processes from plain-language descriptions and answers questions about the data.

- Functional reference: a competitor product ("BOS by WIZONE") seen in a silent demo recording.
  We replicate its **features and behaviour**, NOT its name, logo, copy, colours or exact layouts.
  Product name is **MONO** (configurable via `APP_NAME`, default "MONO"). Brand: MONO — part of the Mono product family (Mono Sheets, Mono AI).
- First customer / tenant: **GGM Minerals** (Goyal Group of Minerals) — quartz slab manufacturer,
  brand Levanto Quartz, plant at Kishangarh (Rajasthan), mines at Tonk, factory at Niwai.
  ~50 active users, Hindi + English speaking staff, many use phones.
- Owner / developer: Nikhil (IT Administrator). He tests and deploys; keep instructions copy-pasteable.

### Non-negotiables
1. Self-hosted on one Ubuntu 24.04 machine (Intel i7-12700, 48 GB RAM, ~1.8 TB disk), via Docker Compose.
2. Reachable from anywhere through **Cloudflare Tunnel** (no static IP, no open ports).
3. Multi-tenant ready: every business table has `company_id`; every query is scoped by it.
4. Mobile-first responsive UI + installable PWA. Every screen must work at 380 px wide.
5. Hindi + English UI strings (i18n from day one; English default).
6. Nothing is ever hard-deleted that has history — soft delete (`deleted_at`) + audit log.
7. All times stored in UTC, displayed in company time zone (default `Asia/Kolkata`).
8. Indian formats: ₹, lakh/crore display (`₹1.31 Cr`, `₹45.36 L`), DD/MM/YYYY, FY April–March.

## 2. Repository layout

```
/apps/api        Fastify app: src/modules/<module>/{routes,service,schemas}.ts
/apps/worker     pg-boss jobs: reminders, checklist generation, escalations, briefs, outbox sender, telegram bot
/apps/web        React app: src/modules/<module>/..., src/components/ui (shadcn), src/layout
/packages/shared zod schemas, enums, state machines, permission keys, money/date formatters, i18n keys
/packages/db     generated Prisma client + company-scope / soft-delete helpers (used by api and worker)
/prisma          schema/*.prisma (one file per module), migrations, seed.ts; prisma.config.ts at repo root
/deploy          docker-compose.yml, Caddyfile, cloudflared config, backup script, INSTALL.md
/docs            module notes, ADRs, screenshots
```

Conventions
- One folder per module on both API and web. Module names: `core`, `org`, `delegation`, `checklist`,
  `slip`, `ticket`, `ea`, `fms`, `docs`, `hr`, `ims`, `crm`, `notify`, `ai`, `integrations`, `search`, `forms`, `lists`,
  `masters`, `records`, `reports`, `platform`.
- **State machines live in `packages/shared/src/machines/*.ts`** as transition tables
  `{from, action, to, guard?, roles}`. API services must call `transition()`; never set `status` directly.
- Every mutation writes an `audit_log` row and emits a domain event (`events.emit('task.assigned', payload)`).
  Notifications are driven ONLY by domain events + notification rules (section 7).
- API errors: `{ error: { code, message, details? } }`. HTTP 4xx for user errors.
- IDs: `cuid2` strings. Human numbers per company per type (`#70`, `BOP/26-27/0004`) via `counters` table.
- Money: store as integer paise (`BigInt`) or `Decimal(14,2)`; format with shared helpers.
- Keep components small; no file > 400 lines. Write tests for every state machine.
- After each phase: run `npm run lint && npm test && npm run build`; fix everything before saying done.

### 3.1 Design system and theming ("Ink & Honey", generated from one colour)
The whole look is generated at runtime from **one seed colour** chosen from a large pool (30 swatches + any colour
picker). Default seed **`#EFC75E`** (honey), grey warmth **45**, corner radius **14 px**, **dark sidebar**,
**primary buttons in the theme colour**. Style reference: GGM's existing "Slabworks" dashboards — charcoal sidebar,
cream page, soft cream cards with large radius, one ink "hero" KPI card per screen, monospace record numbers.

- Generator lives in `packages/shared/src/theme/` (pure functions, unit-tested). Input
  `{ seed, warmth 0–100, radius 4–22, sidebar 'dark'|'light', buttons 'accent'|'ink', mode 'light'|'dark' }`
  → a map of CSS variables. Works in OKLCH: neutrals (page, card, border, text, muted, sidebar, ink) take the seed's hue
  with low chroma scaled by warmth; accent = seed (dark mode clamps its lightness); text on accent = black or white,
  whichever has higher contrast; every text/background pair is checked for WCAG AA and nudged if it fails.
- **Status colours are fixed and never themed**: ok/green, warn/amber-orange, bad/red, over/purple, info/blue,
  neutral/grey — each with bg/text pairs for light and dark, an icon and an EN/HI label, defined once in
  `packages/shared` next to the state machines. Colour is never the only signal. If the seed is close to a status hue,
  Appearance shows a warning.
- Components read only semantic tokens (`--background`, `--card`, `--primary`, `--sidebar`, `--status-bad-bg` …)
  mapped into Tailwind 4 `@theme`; no raw hex in components.
- Customisation levels: **Company** (System Master → Appearance: seed, warmth, radius, sidebar, buttons, logo, app
  name, saved presets: Ink & Honey · Ink · Quartz · Indigo; live preview) · **User** (light/dark/system, density
  comfortable/compact, larger text, language; own accent only if the admin allows it) · **Fixed** (status colours;
  colour-blind-safe option instead).
- Typography: Inter (Latin) + Noto Sans Devanagari (Hindi) + JetBrains Mono (record numbers/codes), self-hosted;
  tabular numbers for money; min 12 px on phones; Hindi gets taller line-height and wrapping buttons.
- Phone (< 768 px): bottom tab bar Home · My work · **+ Capture** (accent) · Alerts · Menu; left menu becomes a drawer;
  dialogs become bottom sheets; tables become card lists; touch targets ≥ 44 px; skeleton loaders; PWA status bar
  colour = sidebar colour.
- A `/dev/ui` style page shows every token and component in light/dark at 380 px; each phase attaches Playwright
  screenshots (380 / 1440, light / dark).

### 5.1 Delegation (one-time tasks)
**Settings defaults**: EA = (user), accept/respond within 30 min, verify within 1 h, reports open on "This week";
toggles **Doer must accept** ON, **EA verifies before done** ON, **Allow re-open** ON.

**State machine**
```
CREATED --assign--> AWAITING_ACCEPTANCE (if doerMustAccept) | OPEN
AWAITING_ACCEPTANCE --accept(doer)--> OPEN
AWAITING_ACCEPTANCE --decline(doer, reason)--> RETURNED_TO_CREATOR
OPEN --moveDate(doer|creator, newDate, reason)--> OPEN (log revision++)
OPEN --addFollowUp(any)--> OPEN
OPEN --passOn(doer, nextDoer, note, newDate, files?)--> AWAITING_ACCEPTANCE (if doerMustAccept and next ≠ creator) | OPEN
AWAITING_ACCEPTANCE | OPEN | PENDING_VERIFY | RETURNED_TO_CREATOR | DONE --addNote(any)--> same status
OPEN --markDone(doer, note, proof?)--> PENDING_VERIFY (if eaVerifies or verifier set) | DONE
PENDING_VERIFY --verify(verifier)--> DONE
PENDING_VERIFY --reject(verifier, comment)--> REOPENED (if allowReopen) --> OPEN
DONE --reopen(creator, comment)--> REOPENED (if allowReopen)
any --cancel(creator|admin)--> CANCELLED
```

### 5.2 Checklists (recurring work)
**Settings defaults**: verifier (user), reminder 30 min before, mark missed after 4 h; toggles **Verifier step** ON, **Photo / voice proof** ON, **Tell the owner about misses** ON.

**State machine**: `MASTER (active) --sweep(due)--> OPEN --tickItems--> OPEN --submit--> PENDING_VERIFY | DONE --verify--> DONE`, `OPEN --windowExpired(auto)--> MISSED` (owner notified), `PENDING_VERIFY --reject--> OPEN`.
- **Checklist master**: name, department/branch, items (ordered lines; each may require photo/voice/value), frequency (daily, specific weekdays, weekly on day, monthly on date or "last day", quarterly, yearly, every N days), due time, window (hours to complete), doer(s) or role, verifier, skip holidays/weekly offs (uses HR calendar), start date, active toggle.
- Worker job `checklist.sweep` every 5 minutes creates runs whose planned time ≤ now+lead; idempotent by (master_id, planned_at).
- Tabs: My checklists · All checklists · Assign checklist · Checklist master · Master changes (audit of master edits).
- KPI tiles: All · Due today ("1 already done") · Overdue ("open past the due time") · To verify ("waiting for a verifier") · Missed ("auto-closed, never done").
- Table: checklist name + department, planned, due + "2d left", status (Running/Done/Missed), progress "0/3 items", tick action → opens run: items with checkbox, photo/voice capture per item, note, submit.

### 5.3 Help Slip (problem → solutions → decision)
**Settings defaults**: receiver (user), approver (user), receiver forward within 4 h, accountability (none), approver decides within 24 h, delegated within 4 h, raiser close 48 h; "Solutions the raiser must give" = 1|2|**3**; toggles **Receiver screens first** ON, **Approver step** ON.
**Flow**: Raiser raises slip (problem + at least N solutions) → SUBMITTED (with receiver) → receiver: forward → WITH_APPROVER, or send back → RETURNED (raiser edits → resubmit) → approver picks a solution (or writes own) → APPROVED → auto-creates a Delegation task for the chosen solution (link both ways) → raiser confirms → CLOSED. Approver may REJECT with reason.

### 5.4 Help Ticket (issue → fix)
**Settings**: raiser / problem solver / process coordinator roles; first reply SLA, fix SLA; escalation levels **Off / 1 level / 2 levels**; toggle **Proof to resolve**; "Who closes the ticket": **Raiser confirms** or **Auto after 24 hrs**.
**Flow**: OPEN (raised) → first reply → IN_PROGRESS → solver fixes + proof → RESOLVED (waiting on raiser) → raiser "fixed?" Yes → CLOSED / No → back to IN_PROGRESS (reopen count++). If no response within SLA or planned fix time passed → ESCALATED (auto) to coordinator (level 1) then HOD/owner (level 2). Roles: Raiser (raises, picks solver + planned fix time, confirms), Problem Solver (replies, fixes with proof), Process Coordinator (rides along and chases; decides nothing).

### 5.5 EA System (owner's personal capture board, run by an EA)
**Settings**: EA (user), week starts Monday, weekly plan day Saturday, waiting cap 6 items, daily brief 08:30, working day 08:00–20:00, information kept 7 days, Someday review every 7 days, delegation follow-up 2 days; toggles **Information stage** ON, **Waiting stage** ON, **Missed day → Someday** ON.
**Flow**: Quick capture (one line, no category; also from Telegram message to bot) → CAPTURED → EA sorts into INFORMATION (reference/fyi) · SOMEDAY (maybe later) · WAITING (parked, capped) · SCHEDULED (day + time slot) · or DELEGATION (creates a Delegation task) → DONE (from any live stage) → CLOSED (no longer carried). Day passes on a scheduled item → back to SOMEDAY if toggle on.
Screens: kanban board by stage, "Owner's weekly schedule" (week grid with meetings/calls/review slots), daily brief message to owner at 08:30.

### 5.6 Weekly MIS
Per person, per week, across modules: planned vs done, on-time %, verifications on time, checklist completion, FMS steps on time. Owner view with all people; export PDF/Excel; auto-send Monday 09:00 to owner and HODs.

## 6. Processes / FMS (Flow Management System)

### 6.1 Concepts
- **Flow** (template): name, "runs are called" (e.g. "Order", "Lead", "Complaint"), departments, Process Coordinator (follows up on time) + backup, Problem Solver (steps in when stuck) + backup, start form fields, ordered **steps**, KPI cards, training video link, status Draft/Published, version (v1, v2… published versions are immutable; records keep the version they started on).
- **Step types**: `TASK` (someone does work) · `DECISION` (yes/no split; each branch → next step id) · `APPROVAL` (a manager says OK; reject → configurable step) · `OUTSIDE` (customer/vendor — waiting on outside) · `AUTO` (system does it: send message, create document, update stock, call webhook).
- **Step config**: name, type, who (users and/or role, "People of Sales, HR"; who can see), backup doer, planned time (value + unit hours/days + anchor: after previous step / after record start / before or after a date field / at a fixed time), checklist lines, entry form fields, documents to generate, stock effect (IMS item in/out), proof required, notify (WhatsApp update to customer etc.).
- **Field types**: short text, long text, number, amount ₹, date, date-time, yes/no, dropdown, multi-select, photo, file, signature, mobile, email, items (line items: item, qty, rate, amount), from a master (customer/item/vendor/person/any custom master), location. Each: label, required/optional, help text, reuse from other flows ("Reuse fields").
- **Time model**: toggle "Working shifts" (count only shift hours, skip holidays and weekly offs) vs "Full calendar".

### 6.2 Screens
- **Processes list** (System Master → Processes card): filters All / Live / Being built / Not started, department chips with counts; groups by department; row: process code (PRC-001), name, "Everything is in place" or "no training video"/"no KPI card"/"Problem Solver missing" warnings, doers avatars, coordinator, problem solver, readiness meter (5/5), status (Live, n running / Being built). Buttons: Import template, Ask AI, **Build with AI**, + New process, List/Grid view.
- **Process editor** (full-screen): left panel "Tell me how it works" (text box + Speak with language select English/Hindi/Hinglish, "Write it again with AI", quick changes "Add approval step", "Add photo proof", "WhatsApp update", "Make it shorter", free text "e.g. add a manager approval after…" + Change). Tabs: Overview · Steps (n) · Coordinator & Solver · FMS report · Dashboard · Video. Steps tab: step list (number, name, doer · planned time · fields) + selected step editor (type radio, Who/Time/Checklist/Entry form/Documents/Stock sub-tabs). Header: readiness "3/5 ready", Saved/Save process, close.

### 6.3 Engine rules
- Starting a record: validate start form, create `fms_record`, compute planned time of step 1, create `fms_record_step` OPEN for its doer, emit `fms.step.assigned`.
- Completing a step: validate step form + checklist + proof; record actual time; DECISION picks branch; APPROVAL waits; AUTO runs immediately in worker; next step planned time computed from anchor using working-time calculator (shifts, holidays, weekly offs from HR settings).
- Doer on leave / absent → use step backup → Buddy rules (section 9.2) → flag "no backup free" and alert coordinator.
- Late detection job every 5 min: steps past planned → `fms.step.late` events; coordinator gets follow-up; problem solver after 2× planned.
- Records are never edited destructively; corrections create history entries.

## 10. Inventory (IMS)

### 10.1 Rule sets (System Master → Inventory → Rules)
- **MAX & review**: daily use from the last (90/**120**/180) days; review every **15** days; raise safety factor when red for **3** days; lower safety factor when purple **50%** of the review period; safety-factor step **0.25**; lowest safety factor **1**. Formula: `MAX = average daily use × lead time (days) × safety factor`. Colour bands: Red (stock < 33% of MAX), Yellow (33–66%), Green (66–100%), Purple (> MAX).
- **OWS & purchase** (Order When Short): order day (e.g. Monday), make orders N days ahead; order qty = MAX − (stock + on order).
- **Turns & NOS**: NOS (non-moving / slow) from < **10** turns a year; NOS target **50%** of stock value; turns growth **26%** a quarter; bottom **20%** by turns offered for stopping.
- **Audit & dead stock**: audit top **50** items by value every cycle; dead after **365** days without movement.

## 19. Decisions log (agreed at kick-off, 31/10/2026 — full reasoning in /docs/adr/0001-kickoff-decisions.md)
1. Project root is `~/mono` (git repo). Start Claude Code from there.
2. Worker reuses API services by importing `@mono/api` modules; one server Docker image runs as `api` or `worker`.
3. Prisma schema in `/prisma/schema/*.prisma`; client generated into `packages/db`, which adds company scoping and soft-delete helpers.
4. Domain events use a transactional outbox: a `DomainEvent` row is written in the same DB transaction as the change; the worker dispatches it. The in-process emitter only feeds SSE.
5. Refresh tokens live hashed in a `Session` table; rotated on every refresh; logout and password change revoke them.
6. Login identifiers (mobile, email) are unique per company; if one identifier matches several companies, the login screen asks which company. Mobiles stored E.164 (`+91…`).
7. Cookies `HttpOnly; SameSite=Lax; Secure` (prod); every mutating request must carry a matching `Origin`.
8. All deletes are soft (`deletedAt`), allowed only when nothing still references the row.
9. Money = `BigInt` paise, sent over JSON as a string; quantities `Decimal(14,3)`.
10. Wall-clock settings (shift start, due time) are stored as minutes from midnight in the company time zone; instants are `timestamptz` UTC.
11. SSE sends a heartbeat every 25 s (Cloudflare idle timeout); Caddy does not buffer `/api/events`.
12. A one-shot `migrate` compose service runs `prisma migrate deploy` before `api` and `worker` start.
13. React 19, TypeScript 6, Tailwind 4, Prisma 7 (pinned at kick-off).
14. Hindi strings are machine-drafted and marked for review by GGM staff.
15. Delegation `REOPENED` is an event (status returns to `OPEN`, `reopenCount++`); `CREATED` is never persisted.
16. HR full-day hours default = 8.
17. Night shifts count on the date the shift starts.
18. Customer tags: `CustomerTag` table only (no `tags[]` array on Customer).
19. Off-machine backup (rclone to Google Drive) is part of the install steps and on by default.
20. PWA manifest/icons in Phase 0; web push sending + per-device opt-in in Phase 2 (install prompt and offline queue in Phase 10).
21. Help Slip "accountability (none)" (answered 02/11/2026): nobody else is held to it — the raiser stays accountable. The other choices make the receiver or the approver accountable. The accountable person is told when the slip is late.
22. Logins created by an admin (add person, login toggle, reset) get a one-time password shown once; the person must choose their own at first sign-in, enforced by the API (`PASSWORD_CHANGE_REQUIRED`).
23. "Paste a list" imports all-or-nothing, reports problems per line, and creates departments/designations that don't exist yet.
24. Org chart: a drop counts only where the pointer is; the head slot wins over its column. HOD of a department is always also a member of it.
25. `seed:demo` holds org data only for now; each later phase adds its own demo data (flows, tasks, checklists, customers, leads, items).
26. Notifications: templates use named placeholders (`{{doer}}`); WhatsApp templates are numbered on submit. Defaults: every §7.3 event × WhatsApp/Email/Telegram × English/Hindi; one rule per event (team → Telegram + in-app + push, clients → WhatsApp + email). In-app is created immediately, once per person per event; other channels wait for the rule's delay and the person's quiet hours (default 21:00–07:00, company time zone). Escalations, test messages and Telegram codes ignore quiet hours.
27. "Reply" for escalations = the person read the notification (app or Telegram "Seen"), or did anything on the same record after it was sent.
28. Channels a company hasn't set up are recorded as SKIPPED when queued; send failures retry 5 times with backoff (30 s → 4 min) then FAILED.
29. WhatsApp approval happens in the provider dashboard (WATI/AiSensy have no reliable submit API); MONO marks templates Pending and reads statuses back from WATI. AiSensy sends through API campaigns named like the template code.
30. One Telegram bot per company (or the .env bot for companies without one), long polling in the worker. A token must not be polled from two places.
31. R/Y/G (per task, cancelled not graded): Green = done on time, never revised; Yellow = 1 day late (any part of a day counts) or revised once; Red = 2+ days late or revised 2+ times; Open = not done and not yet late.
32. Scorecard: a KPI line for the current week grades what was due by now **or is already done** (early work counts at once). Next week's target = the benchmark once met, else this week's actual − 10 points (never below the benchmark). States: meets / off this week / missed twice (this and last week over the benchmark) / no data.
33. Nobody verifies their own work: if the task's verifier (or the EA/creator fallback when "EA verifies" is on) is the doer, the task has no verification step.
34. Checklist runs are created up to 24 h ahead, unique per (master, planned time, doer); saving a master sweeps it immediately. Deleting a master keeps its runs as history, but they leave lists and counts and are never reminded or missed.
35. `delegation.overdue` fires at most once per task per local day; moving the date resets it.
36. People are not notified about their own actions (tests, escalations and Telegram codes excepted).

56. Delegation "Pass on" (answered 03/11/2026): a task done by several people one after another stays one task. The doer passes it on with what they did, the next person and a new due time (it can't be in the past or to themselves). The next person accepts it like a new task (not when it goes back to whoever gave it). A pass-on date is a new part, not a revision. History records each hand-over (from, to, both dates). People who passed it on keep seeing it. Fixed chains that repeat belong in an FMS flow instead. The task counts in reports for whoever finishes it; each earlier part's timing is visible in its hand-over.

They go to the doer, creator, verifier and everyone who did a part (`helper` recipient). The AI only proposes: drafts are shown for review, and nothing is saved until a person accepts. A process draft is checked by MONO; problems it can name (missing time, broken branch, unreachable step, no end) go back to the model once, and the version with fewer problems is kept. The key `end` is reserved for "the record closes".

The model fills a plan (view, columns, filters, group, aggregate) over six read-only `ai_v_*` views; MONO checks every name against the shared catalog, binds every value, always adds `company_id`, and runs the query read-only with a 5 s timeout. The daily summary goes to the owner at 08:45 company time, once a day (`JobMark`), only when AI is connected. An "AI follow-up" rule lets the AI write the Telegram/email text; WhatsApp keeps its approved template, and the template is used whenever the AI has nothing.
62. Rate limits are set per route. Hook lists (`onRequest`) are never shared between routes, because the rate limiter adds its hook to the list and a shared list would carry one route's limit to all the others.
63. One calendar (`companyCalendar`) drives FMS due times, checklist runs, leave days and attendance: holidays, plus weekly offs per weekday (a branch's own win over the company's; none set = the default shift's days). A half weekday counts as working.
64. Attendance is a pure rule (`computeDay`): first IN, last OUT; late past the grace; a half day when late past "half day after", or fewer than the full-day hours (under half of them = absent); a missed punch-out is a half day until corrected, or counts to shift end. A day is settled two hours after the shift ends and settled again after a correction or an import. Days before someone joined are never marked.
65. Absent without leave = someone who punches (any punch in the last 14 days) with no IN by shift start + "half day after", on a working day, with no approved leave. The HOD is told first; the owner too once the confirm time has passed (or right away if the worker first notices late).
66. Buddy cover moves the work: at the leave's start the Buddy becomes the doer and the work shows "Covered by …" (tasks, FMS steps, checklist runs; the sweep makes runs inside a cover for the Buddy). At the end it returns by the rule; "started" = any action by the Buddy on a task since the cover was arranged, data or a note on an FMS step, ticked items on a run. Suggestions follow the company's order and the other-department rule, but a person may choose any active colleague. The HOD is only the last suggestion.
67. Leave: the approver is the person's HOD (or the parent department's); HR (hr.admin or the HR person) can decide any leave; nobody decides their own. Balances are per leave year; comp-off is days earned in the validity window; LWP isn't limited. "Block approval" refuses while work has no accepted Buddy; "Warn only" approves and marks the leave.
68. Telegram buttons on HR messages: the Buddy gets Yes / Can't, the HOD Approve / Reject (only for them, via `telegramActionsFor`). Plain YYYY-MM-DD values in any message show as DD/MM/YYYY.
69. Work patterns (answered 04/11/2026), per person in `EmployeeTerms`: fixed shift (default), hours a day (any time of day, never late; under half = absent, under all = half day, more = overtime), or hours a week (Monday–Sunday; the week, not the day, counts). Hours a day / a week may set a latest start time for the absence alert; without one there is none. A night shift belongs to the date it starts, including the punch card after midnight, absence alerts and the cover board.
70. Pay from attendance is **gross only**. PF, ESI, TDS, payslips and loans wait for the accountant (§9.2). Each person is paid by the month, the day or the hour (paise in `EmployeeTerms.rate`; without terms, the HR-details salary is a monthly rate). Pay rules (`PayRules`, overrides by department < designation < person) set: the month's day value (all calendar days, working days only, or a fixed number), whether days off are paid, what working a day off gives (comp-off by default; extra pay × a day, a fixed amount, or nothing — a comp-off is earned only under the comp-off rule), overtime × the hourly rate, a cut per N late days, and the weekly shortfall. A salary is cut only for days on record (absent, unpaid leave, half days); a day with no record (before MONO was used) doesn't cut a salary and doesn't pay a day wage, and is shown. Days before joining (HR-details DOJ, else when the person was added) are not paid. A running month counts up to yesterday. Pay figures are number paise inside the calculation (they fit easily).
71. Override schemas never carry defaults (`overrideOf`): zod's `.partial()` keeps each field's default, so an override would otherwise reset every answer it didn't mention. A zod error thrown inside a service is a 400, like route validation.
72. Pay is HR's: hr.admin or the HR person in the rules sees and changes it, and nobody changes their own pay except the owner (`*`). The Payroll menu item is shown only with hr.admin (`NavItem.permission`). A month can be closed once it has ended and every day is settled. The closed `PayRun` keeps the figures. Reopening needs a reason and deletes the run, with its figures kept in the audit log.
73. Leave a year can differ by designation or person (`LeaveQuota`): the person's own number, else their designation's, else the leave type's. This year's balance follows at once.
74. Inventory stock (phase 8) is one number per item, kept on `Item.stock` and changed only by `applyMove` in the same transaction as the `StockMove` row. An issue or negative adjustment can't take it below zero: the check and the change are one `UPDATE … WHERE stock >= qty`. Transfers record from / to and move the item's location, not the quantity. Receipts, issues and transfers apply at once; adjustments (damaged, expired, lost, found, audit count) wait as PENDING for an approver (`adjustMachine`).
75. Adjustment approvers: the listed approvers (anyone with `ims.approve` when none are listed); the owner always, when that rule is on; never your own, when that rule is on. With "any one of them" off, every listed approver must say yes (the owner's yes is final).
76. Bands: red below ⅓ of MAX (or under the item's minimum), yellow below ⅔, green up to MAX, purple above it, none without a MAX. A daily `StockSnapshot` keeps each item's stock and the worst band the day saw (red, then purple). The MAX review counts these days. Average daily use is the issues in the window ÷ the window's days, or ÷ the days tracked for a newer item. MAX is rounded up (whole units from 1, three decimals below). Items with no issues in the window get no proposal and keep their MAX.
77. The MAX review proposes; it never changes an item by itself. The morning job (once a day, `JobMark`) writes PROPOSED reviews for items not reviewed for the review period, and tells the reviewers. A reviewer (or `ims.edit`) applies, sets their own safety factor (MAX from the formula), or skips. Either way the item counts as reviewed for that period.
78. OWS: short = stock + on order below ⅔ of MAX, or under the minimum. Order quantity = MAX − (stock + on order), rounded up. "On order" counts open purchase-order lines, drafts included, so a list turned into drafts isn't ordered twice. The list opens N days before the order day (`ims.ows_ready`, once per order day). Red items can be ordered any day. One draft is made per vendor. Purchase orders are `PO/{FY}/{0001}` via `Counter`.
79. Audit cycles are counted from Monday 05/01/2026, every N days (no stored state). Each cycle the top N items by stock value get an `AuditCount`. A difference raises a COUNT adjustment that waits for approval like any other. The owner hears about dead stock once a month.
80. Turns a year = issues' value in the last 365 days (scaled to a year for an item tracked for less) ÷ average stock value from the daily snapshots. Company turns compare the last 90 days with the 90 before. Inventory figures are sent as strings of paise (decision 9) and quantities as numbers.
81. An FMS AUTO "stock" step issues (or receives) the record's item lines, matching each line's item by code, then by name. A line that can't be posted is written on the record's history and skipped; a record never stops on stock.
82. The year plan (phase 9) stores only its inputs (`CrmPlan.data`); every view is worked out by the shared `buildPlan`, which the browser also runs for live previews. Money in the plan is number paise. Every split is `splitExact` (largest remainder, whole rounding units, the leftover to the biggest part), so the year, quarters, months, weeks and days always add up exactly. The seats × months table uses `splitGrid`, so both rows and columns add up. Months follow working days × season × growth within the quarter; quarters follow growth over the one before × tuning.
83. Once a month is changed by hand, the months are the plan (`months` / `monthsGp`) and their sum is the year: "keep the year total" spreads the difference over the other months in proportion; "change it" moves the year. Changing an input that shapes the months then needs `resetMonths` (`MONTHS_EDITED` asks first). The plan goes DRAFT → PENDING → APPROVED (`planMachine`); only the owner approves or sends back; an approved or pending plan can't be edited until it is unlocked or taken back.
84. The CRM configuration is one `CrmSettings.config` (business type, sell to, seats, split, customer rules, after-order steps, NBD, SCOT, own tags, own fields, pages done); seats are lists of people, not a table. Seat targets: CRR / NBD by the share; the owner's own clients come out of CRR; each side is shared by its seats' people (by weight, else equally). The science check names empty seats, the owner over CRR, no lead sources and no owner.
85. The after-order steps are a real FMS flow ("CRM — after the order"), published on save (and again when seats change): doers are the seat's people; "by the promised date" and "after the payment due date" anchor on start-form date fields; documents become checklist lines. Orders (`SO/{FY}/0001`) start a record in it; an order is DONE when its record closes, and cancelling an order cancels its record through the FMS machine.
86. SCOT needs two orders on different days in the last 12 months: the average order, the median gap, a usual day of the month when most orders fall within 2 days of it (monthly or slower; ties → the day closest to all orders), the next order due, and the call N days before (moved back off holidays and weekly offs). Lost customers, and sleeping ones unless SCOT includes them, are off SCOT. Calls are made once a day (`JobMark`): a SCOT call when its day comes (one per cycle), a win-back call every 30 days for sleeping and lost customers. "Later" waits for its date, "not now" waits one rhythm, "lost" marks the customer lost, and an open SCOT call is cancelled if the customer orders anyway.
87. Automatic customer tags are worked out, never stored: top / bottom 20% by 12 months' GP (the rest middle); new by the customer rule (first = until either limit, both = until both); sleeping / lost by days since the last order (or marked lost); vampire = top 40% by sales, paying after the due date and a GP margin below the middle; owner's = flagged or handled by the owner seat. Own tags are `CustomerTag` rows defined in Fields & tags.
88. Receivables: order amount − payments, with payments set against the oldest orders first; an order is due after the customer's credit days; ageing is by days past due (0–30 includes not yet due). A payment can't be more than is owed or dated in the future. Statements go through `crm.payment_due` to the customer's mobile / email and are logged.
89. Leads: an enquiry becomes a lead only when every qualify question is yes, with a value, the next action and its date; every stage move needs a next action. A lead is stuck past its stage's planned days (its owner is told once per stage). Winning makes a customer (or joins one with the same name). People without CRM edit rights see and change only their own leads and calls; the dashboard shows them their own numbers.
90. MeCA grades each sales seat's week against the plan's weeks for the month: orders against the week's share of the person's month target, and calls done against calls due, green at 100%, yellow from 80%, red below.
91. Master rows (phase 10): `MasterRow` keeps the values (`data`), the key (unique per master while the row lives; freed on delete) and the text it shows as (display field, else the key, else the first text field). Imports are all or nothing with problems by line. A Google Sheet is read as its CSV export, rebuilt from the sheet id on docs.google.com only (5 MB, 15 s). "From a master" fields store the chosen row's display text, so a record keeps reading the same after the row changes or goes.
92. Public API: keys look like `mono_<12 hex>_<secret>`; only the sha256 is stored, compared in constant time, shown once. A key acts as its maker with the maker's role at the time of each call, and stops when the maker is disabled or deleted. `/api/v1` calls the same services as the screens (audit rows say `api-key <prefix>`); 120 calls a minute per key. OpenAPI lives at `/api/docs` (production shows only `/api/v1`) and `/api/v1/openapi.json`.
93. Webhooks: a webhook lists exact events, `module.*` or `*` (sign-ins and password resets are never sent). The worker makes one delivery per webhook and event (unique), posts `{id, event, occurredAt, entity, data}` with `X-Mono-Signature: sha256=HMAC(secret, "<timestamp>.<body>")`, waits 10 s, follows no redirects, and retries after 30 s × 4ⁿ up to 6 tries, then FAILED. Customers, orders, payments, stock moves and master rows now emit domain events too (data events).
94. Outgoing calls to addresses people type (webhooks, FMS webhook steps, the WhatsApp provider) pass `assertPublicUrl`: https in production, no credentials, every resolved address public. `WEBHOOK_ALLOW_PRIVATE=1` works only outside production.
95. Google Drive (answered by the brief): owner only, `drive.file` scope, the client secret and refresh token encrypted. Files are always saved on the server first; the worker moves files uploaded after the connection to the "{APP} Files" folder each minute, checks the size and then frees the server copy. Reading tries the server, then Drive. "Stop sending files" keeps the sign-in so files already in Drive still open. Google refusing the sign-in marks the connection "needs attention"; the files stay on the server meanwhile. Files in Drive are not in the nightly backup (Google keeps them).
96. Hardening: uploads are checked by file signature; the web app has a CSP (`script-src 'self'`, inline styles allowed for theme variables) plus HSTS and COOP; every API call counts towards a per-IP ceiling (600/min in production, `API_RATE_LIMIT`) kept by its own small counter, because @fastify/rate-limit's global mode marks a request done once and would switch off a route's stricter limit. At start-up the API checks that `APP_SECRET` still opens the saved secrets.
97. Error monitoring: `ErrorEvent` rows grouped by a fingerprint of company, source, the message's shape (numbers and ids removed), the first stack frame and the route; each repeat counts and reopens a fixed one. Browsers report only when signed in (20 a minute). Admins see their company's errors; the owner also sees system-wide ones (worker, start-up). System Master gains an **Errors** tab (after Appearance).
98. PWA install: the browser's install offer is caught at start-up and shown as a card above every screen (Install), or the Share → Add to Home Screen steps on iPhone; closing it hides it for 30 days.
99. Restore: `deploy/restore.sh <stamp>` restores the database and the uploads archive and starts the stack (migrations run after). A restore needs the original `.env` (`APP_SECRET`), which INSTALL.md says to keep in a password manager, away from the backups.
100. Password resets (09/11/2026, after an accidental reset of the only Owner): a reset from Users always asks first, naming the person and saying it signs them out; nobody resets their own password there (API 400 → Profile → Change password). A locked-out Owner is recovered on the server with `reset-password` (one-time password, `mustChangePassword`, login on, sessions revoked, audit with no actor). `passwordChangedAt` means the person chose the password (Change password, the seeded owner); one-time passwords never set it. The seed's owner password must pass `passwordRule` when the company is created. Add people → One by one closes after each add.
101. Delegation → FMS report (09/11/2026): a process step is graded once — in the week it is done, or, while still open, in the week it falls due once its planned time has passed; on time = done by its planned time; skipped and AUTO steps never count, and an open step counts only while its record runs (on hold isn't late). People shown follow the Weekly MIS (decision 42), whose "FMS steps on time" part uses the same grading and counts in the score. Org chart → Open work (`/api/work/people/:id/open`) follows the same rule: admins see anyone, HODs their team, everyone else themselves. Leftover "arrives in phase N" notices are removed when their phase ships.
102. Phase 11 forms (12/11/2026): every form — process start forms and steps, master rows, records of a record type — is saved through one server pipeline (`apps/api/src/modules/forms`): links → item lines → value lists → formulas → unique → reportable copies. A stage may `check`, `commit` (same transaction as the record) and `release` (the record is cancelled or deleted). A new record's id is chosen before its form is saved (`createId()`), so stages can claim things for it.
103. A picked value is stored as its text, with its link beside it under the reserved key `_refs` (`{ customer: 'Sharma Traders', _refs: { customer: 'customer:<id>' } }`; kinds `customer`, `item`, `user`, `row`, `rec`, `rt`). Everything that read the text before keeps working; `plainValues` / `refsOf` / `mergeData` are the only ways to take data apart or put it together. A link that still holds makes the text the row's current name; a link the field would not offer is dropped and the text stays.
104. Field settings added in phase 11 are all optional with no defaults (`learn`, `list`, `writeAllowed`, `recFilter`, `unique`, `fill`, `locked`, `filterBy`, `formula`, `reportable`, `freeItems`), so definitions saved before read exactly as they did. An absent `freeItems` means "typed items allowed" (older and system-made forms); the builder writes `false` for new item-line fields.
105. Sources of choices are a registry by prefix (`customers`, `items`, `people`, `vendors`, `m:<id>`, `fms:<flow>:<field>`, `rec:<flow>`, `list:<key>`, `rt:<recordType>`). A handler is company-scoped only; whether a person may browse a source is asked by the options and columns routes (`fms.view` for other processes, the type's own view right for record types). Saving a form never needs that right: the form's designer decided what the field reads.
106. Value lists: one live row per value whatever the capitals (`norm`); a new value and one more use are one statement; merge keeps history; hidden values are not offered; a closed list ("only admins add") is closed only once it has values; the public form neither reads nor feeds a list.
107. Unique = one live record per value per form owner and field, held by a database unique index (`unique_values`): closed records keep their value, cancelled and deleted ones free it. Values saved before a field became unique count too (looked up, not race-safe).
108. Formulas are a small language parsed and run by MONO (`packages/shared/src/formula`), never `eval`: numbers, dates, text comparison, `sum` / `count` over item lines, `if`, `ifblank`, `days`, `hours`, `min`, `max`, `round`; `a + 18%` means a × 1.18; a missing value gives no value (never 0); a formula never fails a form. Publish refuses a broken one.
109. Stock on steps: a line that is not in the item master never moves stock (noted, never blocks); short stock blocks the step or, by setting, waits whole as a flagged adjustment; a rejected approval and a cancel reverse with new moves, a decision's "No" and "Close record" do not; a step that moves stock is not a one-tap Telegram button.
110. Record types: status keys are the type's own and the transition table is built from the definition on each request and run by the shared `transition()`. Rights come from the type (a role, or everyone), the Roles matrix (`records.<right>`), or `records.admin`. Nothing destructive is allowed once records hold it; final statuses close a record. A move may start a published process in the same transaction — if its start form refuses, the move is refused.
111. Value paths (`packages/shared/src/fms/paths.ts`): `field` is what the record holds; `field.column` is a column of the row the field links to, read live through the link (bulk look-ups, company-scoped; a broken link reads as empty). Live FMS columns (a view setting on the flow, at most six), KPI sources (`start:item.rate`), document texts (`{{field.column}}`) and process messages (`{{data.field.column}}`) all use it.
112. Reportable fields keep a typed copy in `report_values` (text + lower-case form, number, day — a date-time is kept as its company-local day — and link), written by the form pipeline and removed with the record. A field marked later is back-filled by the worker in batches with a cursor; reports name fields whose copy is not finished. Reports use only the columns every record has and reportable fields.
113. The report engine builds SQL from fixed pieces: field keys and values are bound parameters, names are checked against the source first, the company is always in the WHERE, cancelled process records and deleted records are left out, and the query runs read-only with a time limit. Quarters and years follow the company's financial year. A saved report runs with its reader's rights; a scheduled one runs as its maker, once per slot (`JobMark`), and goes out through the `report.scheduled` rule. Ask may name a saved report it was offered; MONO runs it — the model never writes SQL (decision 60).
114. The request ceiling counts per signed-in person (from the signed access cookie, no database call), per address for visitors, with a flood guard of 20× per address — so an office behind one address is not refused together.
115. Modules added after a company exists (`LATER_MODULES`: records, reports): at start-up a built-in role that holds nothing of such a module gets the default rights; a role an admin has touched is left alone. A data event's `module` is its own prefix, so webhook choices like `record.*` match.
116. Feature strings live in `apps/web/src/locales/parts/<feature>.{en,hi}.json` and are merged at start-up; a part never redefines a section of the main files (tested). A translated sentence that must show literal braces takes them as values (`{{a}}` ← `'{{field}}'`).
117. Phase 12 structure (13/11/2026): Group (the MONO company) → `LegalEntity` (OWN or FRANCHISE; country, currency, tax number, `details`) → `Region` (any depth) → `Branch` (OUTLET / KITCHEN / STORE / OFFICE / HOTEL; `details`, time zone) → `Location`. `BranchManager` rows give a branch its managers (MANAGER) and HR person (HR) and a region its area managers (AREA). A company with no entities and one branch behaves exactly as before.
118. Reach lives in the database client (`packages/db/src/reach.ts`): each request runs in an AsyncLocalStorage slot; after sign-in the person's reach is set and every read (and `updateMany` / `deleteMany`) of a model in `BRANCH_SCOPED_MODELS` gets "no branch, or one of my branches, or a row I am part of". The worker and seeds have no slot and are unfiltered; `withReachOf` acts as a person outside a request; `reachSql` gives the same condition to hand-written SQL. A model with a `branchId` must be listed as scoped or as free with a reason (a test checks the schema). Rows with no branch are group-wide.
119. A role has a reach (`own`, `branches`, `entity`, `group`; existing roles are `group`). A person's branches are their home branch, the ones they also work at, the ones they manage or are HR of, every branch of the regions they are area manager of, and a branch they are lent to today. The top-bar switcher sends `x-mono-branch` (a branch id, `r:<region>` or `e:<entity>`); it narrows strictly (not even the person's own rows elsewhere) and never widens.
120. Work carries the branch of the person it starts with (a task: the doer's; a slip, ticket, record, order: the maker's; a paper: its record's; a checklist run: the template's branch or plan, else the doer's). The owner has no home branch, so what they make is group-wide unless they choose a branch.
121. Approval routing (plan decision 14): no built-in order. `ApprovalRoute` holds a ladder per kind (`hr.leave`, `hr.correction`, `ims.adjustment`, `slip`, `ticket`) for the group, an entity or a branch (branch > entity > group). One decision decides. "From an amount" starts the request at that step and leaves the earlier steps out. A step nobody holds is passed over only if it says so. "Go up after N hours" lets the next step decide too. Nobody decides their own request; the owner always may. With no ladder for a kind, the module's own rule stands (HOD / HR for leave, the listed approvers for stock …). Slips take the first step as receiver and the next as approver; ticket escalation level n goes to step n.
122. `hod` in a notification rule means the route's first people when the event carries `approverIds`. Place recipients (`branch_manager`, `area_manager`, `branch_hr`, `department_head`) are read from the branch in the payload, else the home branch of the person the event is about.
123. A process step with several doers goes to those at the record's branch, then its region, then anyone — least busy within that. Leaving the branch writes `doer_outside_branch` on the record.
124. A checklist template may list branches (`perBranch`): each gets its own runs, doers, due time and clock; the template's own doers are then not used. A plan with no doers makes no runs.
125. Flow-designer people can be set per branch (`ModuleBranchSetting`, person keys only); times, rules and switches are always the company's.
126. Closing a branch sets `closedAt` and `deletedAt`: it leaves pickers and the structure while history keeps its id. People and open work must move first. Copying a branch never copies people.
127. Document numbers: a type's `series` is `company` (default, unchanged), `entity` or `branch`; the place's `seriesCode` goes into the number (`INV/RJ/26-27/0001`) and into the counter key. A place with no code uses the last four characters of its id. A paper with no branch keeps the company series.
128. Branch history: `BranchStay` rows say where a person works from a day; the first branch of someone who had none counts from the beginning. `User.branchId` is where they are today, kept in step when a move is saved and by a job on the day a planned move begins. `BranchLoan` overrides the day's branch while someone is lent. Attendance days are stamped with the day's branch; a month's gross is split over branches by days with `splitExact`.
129. Punching: a person may punch inside any geofence of any of their branches (a branch can have extra gates in `details.fences`); the home branch's answer counts when none matches.
130. HR rule overrides layer company → entity → branch → department → person. Pay-rule overrides add `entity` below department. Minimum wages are rows typed by the accountant (entity and / or designation → monthly amount); pay below them is flagged, never changed. A pay run has an `entityKey` ("" = the whole company); a month is closed for the whole company or entity by entity, never both.
131. Holidays may be for everyone, a country, a state, a legal entity or a branch; a branch's calendar is everything that applies to it. Leave days a year: person, else designation, else entity, else the leave type.
132. Money in any currency is whole minor units plus a code (`formatMoney`, `minorUnits`); rupees keep `formatINR`. Group totals are in rupees with `ExchangeRate` (one per currency per month); a currency with no rate that month is left out of the total and named. An entity's tax regime is a profile in its `details.tax` (regime, the tax number's name, invoice title, rates, a legal line) — no country's tax is built in.
133. A branch's time zone (else the company's) is the clock for its people: `HrPerson.tz`, the calendar's `tz`, "today" for absence and settling, checklist plans and notification quiet hours.
134. Franchises: a person whose home branch is in a FRANCHISE entity is isolated — only that entity's branches, people and entity, no group-wide rows except brand content marked `shared` (master rows, checklist templates), which they can read and never change. Group people without `franchise.view` see everything except the franchises (`exceptBranchIds`). Brand functions (royalties, audits, export, archive) need `franchise.admin` and are never open to a franchise's own people.
135. Royalty for a month = max(sales × % + fixed fee, minimum guarantee), on the sales orders of the franchise's branches (until the POS exists), one invoice per franchise per month (`ROY/{FY}/0001`), raised by the brand team after the month ends. A brand audit's failed points become proof-required tasks for the outlet's manager. Renewal reminders go 30 days before, 7 days before and on the day, once each (`JobMark`). A franchise is archived only after its export (a zip: JSON per kind of data, its people's files up to 200 MB, a manifest); archiving signs its people out for good and retires its branches and entity.
136. The process-step watcher pages through every open step (500 at a time, by id); a fixed "first N" with no order starves later rows.
137. Phase 12M money (13/11/2026): a `Party` is anyone MONO deals with; a CRM customer is a party with the same id and code, kept in step by the CRM (and made on the spot if a paper needs a customer that has none). Vendor names typed on items and purchase orders become parties only when a person matches them (`PartyAlias`); nothing merges by itself.
138. One `Bill` model for INVOICE, CREDIT_NOTE, DEBIT_NOTE, RECEIPT, ADVANCE, PURCHASE_BILL, VENDOR_PAYMENT and CHALLAN, in minor units with a currency, run by `billMachine` (DRAFT → ISSUED → PART_PAID → PAID, CANCELLED). A draft has no number and can be edited or discarded; an issued paper is never edited. An invoice or purchase bill is cancelled only by a credit note for what is still open; a money paper (receipt, payment, advance) is voided with a reason, which puts back what it settled and turns its voucher round with a second one.
139. Tax is data (`TaxRate`: code, percent, from-date, optional price slabs, optional entity): the rate used is the latest one starting on or before the bill's date. The split comes from the seller's entity tax profile and the two states: same state CGST + SGST (halves), another state IGST, a VAT profile one tax, no profile no tax. `computeBill` (shared, also used for the live preview) works lines, charges, discount, tax inside or on top, and round-off; MONO ships no rates.
140. Bill numbers: `INV / CN / DN / RCT / ADV / PB / PAY / DC` + the legal entity's series code + FY + 4 digits through `Counter`. A paper raised from something that already has a number (a CRM order) keeps that number.
141. Money against papers: a receipt or vendor payment is set against the bills named, else the party's oldest unpaid papers first; what is left over stays on the money paper as unused credit. Ageing counts days past the due date on the company's clock (0–30 includes not yet due); "overdue" is strictly after the due date.
142. Every issued paper writes a `Voucher` of debit and credit lines against MONO heads (party, sales, purchases, each tax, each payment mode, round-off) that always balance. The Tally export refuses until every head used has a ledger name (`TallyMap`); a party's ledger is the party's name.
143. The CRM runs on the money core without changing its screens: an order is an issued invoice with the order's number, a payment a receipt (against its own order when it names one and fits), a cancelled order a credit note. `carryOverCrm` (worker, every 5 minutes, in batches, oldest first) does the same for what existed before; it is safe to run again.
144. A day close is one row per branch and day: for each payment mode, the day's money papers (in − out) against what was counted. A closed day is not closed twice. Money screens take "today" from the company's time zone, never the browser's.
145. Phase 13 stock per location (13/11/2026) — changes decision 74: stock is held in `StockBalance` rows (item, location, batch); `Item.stock` stays as the total, so bands, MAX, OWS and turns read on. Location "" is the company's main store (stock from before locations — moved there by migration, or adopted the first time an item moves) and "~transit" is goods on the road. Every change still goes through `applyMove`, which takes from / puts into balances in the same transaction; a decrease is one guarded UPDATE per balance row. The main store and transit belong to people who see the whole group; others see only the locations of their branches (`reachPlaces`).
146. An item's tracking is chosen once (QTY, BATCH, SERIAL, LOT) and can't change after it has stock. An item has one stock unit; other units are `{ unit, factor, serve? }` (a serving such as a peg is sold, a container such as a bottle is what stock is read in: "11 bottle + 450 ml open"). Every move keeps the unit typed and the converted quantity. A second unit (`qty2`, a weight) follows the stock in proportion.
147. Issues are first expired first out; an expired batch (expiry before today on the company's clock) is never picked, even by name — only wastage, a vendor return, a count and a transfer's receipt may take one. A serial piece is one unit with its own number, cost, weight and attributes; it never moves without its number. A batch's or piece's barcode wins over the item's when a code is scanned.
148. Cost: a balance holds the value of what is there (weighted average = value ÷ quantity); a receipt keeps the exact value typed (a case at ₹12,000 is not 9 000 × 133 paise). Recipe cost uses each ingredient's company average (its rate when there is no stock). FIFO values a location's stock from its newest receipts. The method is a stock rule (`stock.valuation`).
149. Transfers follow `transferMachine`: REQUESTED → APPROVED → DISPATCHED → RECEIVED (differences) → CLOSED. The supplier is named, else the asking branch's supply route for the first item's category, else its default. Only the supplying side approves and dispatches; only the asking side receives; differences are decided by a stock approver who did not receive them (short and damaged are written off from transit, extra is taken in). An emergency needs a reason and, by rule, a yes from both sides (`approvals` keeps `from:<user>` / `to:<user>`). A store's own transfer (DIRECT) starts approved. A move between two locations of one branch is a plain entry; between branches it must be a transfer.
150. Papers on dispatch between two branches: both under one tax number (or none) → a CHALLAN; two tax numbers → an INVOICE from the sender's entity with the items' tax codes, and on receipt a PURCHASE_BILL in the receiver's entity. The other side is a party made for the legal entity (`ent_<id>`, or `co_<company>`). Priced by the route: cost, cost + %, or a price list (cost when the list lacks the item).
151. Recipes: `outputQty` of the item from lines `{ item, qty, unit, yield %, wastage % }`; raw needed = qty ÷ yield × (1 + wastage). Saving makes a new version and switches the old off. A DISH is never stocked: selling or using it opens its recipe (any depth) down to stocked items. A MAKE item is produced: finishing a production order takes the recipe's ingredients for the planned quantity, puts what was really made in as a batch (number = the order's, expiry from the shelf life) at its real cost, and keeps made − planned as the yield variance.
152. A goods receipt records what was accepted and rejected; against an order it gives the quantity difference (against what was still due — more is taken in as an excess) and the rate difference, moves the order through `poMachine`, and makes the latest rate the item's rate. It raises the vendor's purchase bill only when the typed vendor is matched to a party. A return to the vendor takes the stock out and credits that bill.
153. Wastage is an ADJUST move with a reason and `refType: 'wastage'`: worth up to the rule's limit it applies at once, over it it waits for a stock approver like any adjustment. A closing count compares each item with the location's stock at submit and with what recipes and sales took since the last approved count (theoretical): the difference over that is the variance %, flagged above the rule's limit (or whenever something differs that no recipe explains). A count with differences waits for an approver who is not the counter; approving posts COUNT adjustments. A blind count hides the system figure from whoever opened it.
154. Price: an item with a rate-board key is priced by the newest rate on or before the day × its factor (per unit of weight when it is priced by its second unit); otherwise the most specific live price list that holds it (party kind + branch, then party kind, then branch, then everyone; newest start wins); otherwise its own selling price; otherwise it can't be sold until a price is typed. A counter sale (`/api/ims/sell`) bills through the money core and issues the stock in the same transaction.
155. Phase 14 hospitality (13/11/2026): a module of its own (`hosp`, rights `hosp.*`), **off** until an admin switches it on (`HospSettings.enabled`); `me.company.hospitality` shows its menu section (`NavItem.needs`). An outlet belongs to a branch and takes stock from one location of that branch (or the main store). Outlets, rooms and room types are limited to a person's branches in the hospitality services (`branchWhere` / `inReach`); the menu is the company's, with items that may be limited to outlets.
156. An outlet's charges are its own: a service charge % that is always the guest's choice, packaging, delivery, round-off, and an optional tax code on the charges. Tax codes everywhere in hospitality must exist in the money core's tax rates — none is built in.
157. Kitchen tickets: a menu category's tickets go to the station its route names at the outlet, else the outlet's default route (category ""), else the outlet's first station. Deleting a station drops its routes; deleting a printer clears it from stations and outlets.
158. A floor plan is a 24-cell-wide grid; a table has a place (x, y), seats, a shape, a section and whether it can be joined. Table names are unique in an outlet whatever the capitals; room numbers are unique in a branch. A connecting door is written on both rooms; deleting a room clears it from its neighbours.
159. Hospitality rules (`HospRules`): discount types; per role the most it may give by itself (% and / or ₹) — within the limit it is allowed, above it it needs an approver, and a role with no limit gives nothing by itself; who approves; no-charge reasons and who may use them; the day close (business-day cut-off — a bill before it belongs to the day before — closers, denominations, blind cash). Saving changes only the parts sent.
160. The menu: an item sells a stock item (a dish with a recipe, or a stocked item); a variant has its own price and a share of the recipe (half = 0.5) or its own stock item; a modifier option may take stock with it; a combo sells menu items together and holds no combos or variants. The price at an outlet at a time is: this outlet's price in a running time band, a band for every outlet, this outlet's own price, the menu price. Windows may cross midnight (the late part belongs to the day it started). An item is 86 when a person switched it off, or when the outlet's location can't make one (expired batches don't count; an item with variants only when no variant can be made; a dish with no recipe is never switched off for stock).
161. Phase 15 POS (13/11/2026): an order (`orderMachine`: OPEN → BILLED → PAID, or CANCELLED while nothing was fired) belongs to an outlet and a **business day** (the outlet's clock and the cut-off rule); orders and kitchen tickets are numbered per outlet per business day through `Counter`. A table has one running order. An item's price, station, tax code and stock item are taken from the outlet's live menu at the moment it is added; an item that is 86 or outside its hours is refused.
162. Kitchen tickets: firing held items makes one `Kot` per station (`kotMachine`: NEW → READY → BUMPED, recall back to NEW, CANCELLED when every item on it is voided). Items follow `orderItemMachine` (HELD → FIRED → READY → SERVED, VOID). The kitchen display is polled; a ticket's colour is the pure `ticketAge` rule (amber from 10 minutes, red from 20).
163. Voids: a HELD item is taken off with no reason. A fired item needs a reason; it is voided at once when its value is within the role's `voidPaise` or the person is an approver (listed approvers, `hosp.approve`, the owner), otherwise a `PosApproval` waits and the item is marked. Nobody decides their own request. "Cooked" writes the dish's ingredients off the outlet's location as RETURNED_DISH waste; not cooked takes nothing. A bill can't be made while a void waits.
164. A check is one bill of an order: an INVOICE in the money core (party = the order's or check's party, else one "Walk-in guest" party per company), raised and issued by the system in the same transaction. Menu prices are before tax. The service charge is a charge line on table and room service only, on the amount after discount, and is left out when the guest refuses or the bill is no-charge; takeaway and delivery add packaging, delivery adds the delivery charge. A discount is PERCENT or AMOUNT off the food; above the role's limit (or a no-charge by someone who may not give it) the whole request waits as a `PosApproval` and is billed as the asker when approved. A no-charge bill totals nothing and is settled as it is made.
165. Splits: by item or by seat changes each item's `checkNo` (several bills); equally or by amounts keeps one bill and records the parts it is paid in (amounts must add up to the total). A cancelled check keeps its row and number; the same check can be billed again under a new number.
166. Payments are RECEIPT papers set against the check's invoice, one per mode; a mode with `needsRef` refuses without a reference; a ROOM payment takes the room number as its reference (a real folio comes with Phase 17); COMPANY credit makes no receipt — the invoice stays owed by that party — and is refused on a walk-in bill; COMPLIMENTARY is not a payment (use no-charge). Never more than is due. Tips are kept on the check per steward and are not part of the invoice.
167. Stock on settlement: when the last check of an order is paid, each live item takes its recipe (× the variant's share) and its add-ons' stock from the outlet's location, as RECIPE issues. What the location is short of is written on the item (`stockNote`) and skipped — a payment never fails on stock.
168. Cancelling a bill needs an approver and a reason: its receipts are voided in the money core, a credit note for what is open undoes the invoice, and the order returns to OPEN. An order that is already PAID is not cancelled from the POS (its stock is taken): a credit note is raised in Money.
169. Day close: the Z report of a business day (sales, tax, charges, discounts, no-charge, voids, money by mode, tips) and the cash counted by denomination are kept on `PosDay`. A day closes only with no running order and no unpaid bill, by a listed closer or an approver; with a blind count the expected cash is hidden until it is closed (the owner sees it). A CLOSED day refuses new orders, lines, bills and payments; only the owner reopens it, with a reason, kept in the audit log. A shift is one cashier's X report: what they took since it opened, plus the float.
170. Printing: a ticket or bill is ESC/POS bytes in a `PrintJob`. NETWORK printers are sent to by the server (ip:port, default 9100) right after the request and again by the worker each minute; five failures make the job FAILED. AGENT printers are never dialled by the server: a branch's site agent pulls its queued jobs and reports each done. Text is plain ASCII (₹ becomes "Rs", other scripts "?") because printer code pages differ.
171. Devices and lost connections: `PosDevice` holds bill numbers reserved from the entity's invoice series (`reserveNumbers`); a bill may be made under one of them exactly once. Orders and order lines accept a `clientId` made on the device — the same request sent twice is made once. The POS screen keeps what could not be sent in the browser's storage and sends it in order when the server answers; a request the server refuses leaves the queue and is reported.
172. Phase 16 reservations (13/11/2026): a booking belongs to an outlet and takes its table(s) from its start for a length set by the party size (`Outlet.booking`, every part with a default). Times are kept as the outlet's local day + minutes (past 1440 = after midnight, the same evening) and as instants; overlap is checked on the instants. Every change that takes or moves a table holds one advisory lock per outlet for its transaction, so a table is never in two live bookings that overlap. REQUESTED, CONFIRMED, REMINDED, ARRIVED and SEATED keep the table; CANCELLED, NO_SHOW and FINISHED free it.
173. Best fit: the smallest free table that seats the party; else joinable (`combinable`) tables of one floor — the fewest tables (at most four), then the fewest spare seats. A table chosen by hand is only checked for being free, not for its seats. Availability looks at bookings only — a walk-in order still at a table is not counted (the POS floor shows the table as Reserved from `floorHoldMin` before instead).
174. `reservationMachine`: confirm (not while a deposit is due), remind, arrive, seat, finish, cancel (until seated; by staff, the guest's link or the clock), noShow (staff at any time; the clock only after `holdMin`), restore (a no-show who came — only if the table is still free). The worker's minute sweep reminds once (`reminderHours` before; never a booking made inside that window), marks no-shows, and cancels a request nobody confirmed by its time.
175. The public booking page is per outlet (`bookingToken`, made when the page is first switched on): slots without table names, the largest party, the days ahead and the offered times enforced, a signed sum (the helper now lives in `lib/challenge.ts`, shared with the public form), a honeypot, 10 bookings a minute per address. The guest's link (`Reservation.token`) shows and cancels one booking. Online bookings confirm by themselves unless the outlet says a host confirms each (`autoConfirm`), or a deposit is due.
176. Deposits: from `depositFrom` guests, `depositPerHeadPaise` each (a host may also set one by hand while unpaid). The booking stays REQUESTED until the deposit is recorded as an ADVANCE paper for the guest's party (`guestParty`, code `GST-…`, made on first need); then it confirms. `depositState`: DUE → PAID → USED (set against the bill), or on cancel / no-show KEPT or REFUND_DUE by the rules (`cancelFreeHours`, `noShowDeposit`), then REFUNDED when the advance is voided — any host for REFUND_DUE, an approver for KEPT. No payment gateway is called (plan decision 3 open).
177. An advance against a bill (`money/credit.ts`): `applyCredit` settles an invoice from an ADVANCE or RECEIPT's unused amount and raises the money paper's `settled`; `releaseCredit` undoes it. On a POS check it is a payment of kind ADVANCE (no receipt of its own); cancelling the check releases it back to the guest. Seating a booking whose deposit is paid opens the order in the guest's party name so the invoice and the advance belong to the same party.
178. Seating a booking or a waitlist party opens the POS order through `openOrder` (the table must have no running order) and stamps `PosOrder.guestId` / `reservationId`; when the order is paid the booking is FINISHED by the system. The order's note carries the occasion, requests and allergies to the kitchen.
179. The waitlist quote is the time the party's table is expected free: a running order frees its table at opened + the stay for its covers (never sooner than 10 minutes from now), a booking due within the party's own stay blocks its table until it ends, and each party already waiting (that these tables could seat) takes the next table to come free; rounded up to 5 minutes; null when no single table seats the party.
180. Guests: one `Guest` per mobile (E.164; ten digits are read as +91) per company, shared by every outlet. A booking finds the guest by mobile and never overwrites the profile. Visits, spend, favourites and no-shows are worked out from paid orders and bookings within the reader's branches, never stored. Consent is one current entry plus a log that only grows (`{ marketing, source STAFF | ONLINE | GUEST, at, byId, note }`); not ticking the box online records nothing. Deleting is soft and refused while a booking is still to come.
181. Phase 17 hotel (13/11/2026): a property is a branch with rooms; its rules and its **business date** are one `HotelSettings` row (made the first time the property is used, at today on its clock). The business date moves only with the night audit; bookings, charges and money papers of the hotel are dated by it. Front desk and reservations need `hosp.create`, supervisors (allowances, blocks, restrictions, inspection, the night audit) `hosp.edit`, rate plans and rules `hosp.admin`.
182. A stay has one `RoomNight` row per night with that night's rate; a room that is out of order has one per blocked day. `RoomNight` is unique on (room, day), so two stays — or a stay and a block — can never share a room on a night; a night with no room yet has `roomId` null. Rooms left to sell for a type on a day = its rooms − nights sold − blocked rooms − what a HELD group block has not yet had picked up. Changes to a property's rooms hold one advisory lock per branch.
183. Rates: a night = the plan's base (or weekend) rate for the room type, × the season it falls in, + extra adults above the type's usual number and children, − the length-of-stay tier, rounded to whole rupees; each night's rate is fixed on the booking when it is made. Nights added later are priced then. A free upgrade sleeps in a better room at the booked type's rate (`Stay.roomTypeId` is the type charged; `RoomNight.roomTypeId` the type slept in); a paid one (`rerate`) charges the new type from that night.
184. Restrictions (`RoomDay`): stop-sell on any night, closed to arrival on the arrival day, a minimum stay (the larger of the plan's and the arrival day's). A group block's own pick-ups skip the open market's restrictions but never its own count or dates. A block gives back what is not picked up once the business date is past its release date (worker).
185. `stayMachine`: BOOKED → CHECKED_IN (a room and the ID with its photo and signature) → CHECKED_OUT (every folio closed); BOOKED → CANCELLED / NO_SHOW. Cancelling or a no-show frees every night and puts the plan's charge (cancel: none while free, else first night / % / all; no-show: none / first night / all) on folio 1 with the room's tax code, to be settled like any folio.
186. Form C: a guest whose nationality is not Indian gets `formCDueAt` = check-in + the rule's hours (24); the managers are told once, six hours before; it is marked filed only when passport, visa and travel fields are all there; a CSV lists the foreign guests of a span.
187. Folios: charges are kept before tax (`FolioLine`); a payment line is the money taken (an advance paper or a receipt). Routing (`Stay.routing`) sends kinds of charge to a folio; a corporate booking starts with folio 2 for the company and ROOM, EARLY, LATE routed to it. When every folio has been closed mid-stay, the next charge opens a new folio for the guest — a charge is never lost. An allowance marks a line voided with a reason (supervisor); after the invoice a correction is a credit note.
188. Closing a folio (`settleFolio`): its charges become one INVOICE for the folio's party on the business date — one line per charge, so each room night's tax comes from the slab its rate falls in (`TaxRate.slabs`); advances are applied first, then the money given, one RECEIPT per paper paid. The guest's own folio must end at zero; a folio whose party is not the guest may be closed `onCredit` (the invoice stays owed and shows in receivables). An advance left over stays the payer's unused credit.
189. POS and the hotel (changes decision 166 where the outlet's branch is a hotel): a ROOM payment makes no receipt — the check's invoice stays owed and a FOOD line (`refType: 'pos_check'`) goes on the folio of the guest checked in to that room; nobody checked in → refused. That line is not invoiced again: at folio settlement the restaurant's own invoice is paid first by its own receipt. Cancelling the check takes the line off the folio. At a branch with no `HotelSettings` the POS keeps decision 166.
190. 191. Housekeeping: `Room.hkStatus` (DIRTY, CLEAN, INSPECTED, OUT_OF_ORDER, OUT_OF_SERVICE) follows `roomHkMachine`; occupied / vacant is read from the stays. A cleaning task (`HkTask`, one per room, day and kind) is done only when every checklist line is ticked; inspection and "clean again" are a supervisor's. Cleaning issues the rule's linen and amenities, and the minibar check issues what was taken, from the housekeeping location — short stock is skipped, never blocking.
192. A room off sale is a `RoomBlock` with `RoomNight` rows for its days (so a booking on those days refuses it) and, when someone is named to fix it, a help ticket; the worker gives the room back (DIRTY) when the ticket is CLOSED or CANCELLED, and a block with an open ticket cannot be released by hand. A guest request is a help ticket for the property's request person due in the rule's minutes; from the room's QR link (`Room.token`) it is raised in the name of whoever checked the guest in, and only while a guest is checked in to that room.
193. Phase 18 (13/11/2026): a branch's own banquet and bar rules are one `BranchRule` row (`{ banquet, bar }`, every part with a default; saving changes only what is sent). Sales and the floor need `hosp.create`, managers `hosp.edit`, set-up `hosp.admin`.
194. A banquet event (`banquetMachine`): ENQUIRY → QUOTED → CONFIRMED → COMPLETED → CLOSED; LOST from an enquiry or quotation, CANCELLED (a manager) from a confirmed booking. A quotation = the package's price per plate × guaranteed covers + hall rent + extras − discount, taxed by the package's, the hall's and each extra's tax code; the covers must fit the halls in the event's setting. Confirming needs the rule's share of the total in ADVANCE papers (`sourceType: 'banquet'`) and free halls: CONFIRMED and COMPLETED events hold their halls, and one advisory lock per branch makes two confirmations of one hall and time impossible. Enquiries and quotations hold nothing.
195. A confirmed event carries its BEO (`beo` notes per department, `beoVersion`, `beoSentAt`): sending tells the branch's managers; a re-quote after confirmation is a revision — version + 1, not yet sent, the indent worked out again. The indent is the package's dishes exploded through their recipes × guaranteed covers against the event's stock location. The event-day checklist is copied from the branch's rules at confirmation and must be fully ticked before the event is completed.
196. Completing an event takes the food for the covers that came from the stock (a dish whose ingredients are short is noted and skipped), raises the final INVOICE for max(actual, guaranteed) covers, and sets the advances against it. Settling takes receipts for the balance — the guest pays in full; a company that booked it may be left owing — and closes the event. Losing an enquiry voids its advances; cancelling a booking voids them when it is at least `cancelFreeDays` ahead, else keeps them: an invoice "Cancellation charge" for the amount paid, settled by the advances.
197. The excise register is built from the stock register of each of the branch's locations for a day, kept to items whose category is one of the branch's liquor categories, in bottles (the item's smallest container unit) and ml. The export has one layout, RAJASTHAN — a brand-wise daily register with the licence in its heading; it is not an official form and must be checked before filing.
198. A dry day (a date in the branch's bar rules) marks liquor as switched off in the outlet's live menu for that calendar day — by the menu category's name, the stock item's category, or any ingredient of the dish's recipe — so the POS refuses it like any 86'd item.
199. Compliance: a `ComplianceItem` has the day it runs out (or is next due); its state is VALID, EXPIRING (inside its longest reminder) or EXPIRED. The worker tells the branch's managers and the owner once per step (each of `remindDays`, the day, run out — `JobMark` keyed by the item, its due day and the step). Renewing sets a new day and keeps the old in `history`; with `everyDays` the next day is today + N. A temperature reading outside its point's limits is refused without what was done, then kept as not-ok and told to the managers at once.
200. Phase 19 integrations (13/11/2026): a `Connection` is one per kind and scope — CHANNEL per property (scope = the branch), GATEWAY and EINVOICE per company. Keys are encrypted with `APP_SECRET`, never returned and never in the audit log; a later save without keys keeps them, another provider must bring its own; removing switches it off and wipes the keys. Only `integrations.admin` changes one. Every call out goes through `callOut` (public addresses only, https in production; 15 s; logged in `SyncLog`; the connection keeps its last success and last error).

Channel manager: MONO speaks one plain JSON contract — POST `{base}/ari` (rows of room code, rate code, date, rooms left never below zero, price, stop-sell, closed to arrival, minimum stay), GET `{base}/bookings?since=`, and bookings posted to MONO's webhook `/api/hooks/channel/<token>`. Only mapped room types are sent, priced by the connection's plan. A push that fails waits and is sent again by the worker every five minutes; five tries, then FAILED.

It is never refused for restrictions or a full house: with no room left it is taken and flagged `overbooked` for a person. `modified` moves its nights; `cancelled` frees them through the stay machine as the system. Bookings are source WEBSITE with no actor.
204. Payment links (`PayLink`): made at the company's gateway for a table deposit (what is due), a stay's or banquet's advance (the amount typed) or a restaurant bill (what is due); one waiting link per thing and amount. The webhook `/api/hooks/gateway/<token>` is read as raw bytes and its signature checked (Razorpay: HMAC-SHA256 of the body with the webhook secret; Cashfree: base64 HMAC-SHA256 of timestamp + body with the client secret). A paid link records the money through the same service a person at the desk uses, as the link's maker, under the mode the connection names (else one called "Payment gateway"), with the gateway's payment id as reference. A link is paid once; an amount that differs from the link, or a payment that cannot be recorded, is kept on the link and shown on the health screen — never recorded silently. No refund is sent to a gateway.

206. Delivery aggregators: an order is tagged with the aggregator and its order number there (unique among live orders) while it is running and unbilled; its bill is in the aggregator's party (`agg_<name>_<company>`) and is closed with the COMPANY-kind mode "Aggregator" — no money in, the invoice owed by the aggregator. 210. Phase 20 packs (13/11/2026): a pack is a JSON file of set-up (`packSchema`): roles, tax-code shells, value lists, masters with rows, items with their extras, record types, processes, checklists, saved reports, words and module switches. Things point at each other by token (`@pack/master/<key>`, `@pack/rt/…`, `@pack/flow/…`, `@pack/role/…`, built-in roles as `@pack/role/builtin_hod`, `@pack/me` = whoever installs); the installer swaps tokens for ids, the exporter swaps them back and turns every person into `@pack/me`. Only `core.admin` installs, exports or removes.
211. Installing: each thing is made once. What the company already has (a role, master, process, checklist or report by name; an item by code; a record type by prefix; a tax code; a list value) is taken over as it is and never changed; what the pack made earlier and still exists is left as the company has it now. So an upgrade adds only what is new, the same version again changes nothing, an older version is refused, and two packs share what both name. Rows go only into a master the pack has just made. A new tax code is a shell at 0 % from 2000-01-01 (decision 139). Processes are made empty, record types next, then the processes' steps are saved and published — so each can point at the other. `PackInstall.made` lists what the pack made or adopted.
212. A pack's record types go in a left-menu section named after the pack. Removing a pack sets `removedAt`: its words go and nothing it made is touched; installing it again finds its things and makes nothing twice.
